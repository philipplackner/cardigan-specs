# Decisions: api-conventions

Confirmed with Philipp Lackner on 2026-11-04.

## Summary

This change defines the cross-platform conventions every Cardigan API endpoint follows: which contract is authoritative, base path and versioning, wire data formats, the error model and its codes, auth token conventions, ordering and move semantics on the wire, and the versioned board export file format with its import mapping rules. It does not define individual endpoints, DTOs or feature flows; those come code-first from the backend and from later feature specs.

## Decisions

### D1 — Scope
- **Question**: What should this change cover?
- **Decision**: Cross-cutting API conventions, auth token conventions (lifetimes, transport, rotation, logout scope) and the board export file format including its import mapping rules. Full auth flows and other feature behavior come in later feature specs.
- **Alternatives**: Cross-cutting only; everything including full auth and import/export flows.
- **Depends on**: —

### D2 — Spec layout
- **Question**: How are the new specs organized?
- **Decision**: Several flat specs: `api-conventions`, `api-errors`, `api-auth-tokens`, `board-export-format`.
- **Alternatives**: One single `api-contract` spec.
- **Why**: Matches the existing flat layout (`text-length`, `domain-*`).
- **Depends on**: D1

### D3 — Authoritative contract
- **Question**: Which contract wins when the generated OpenAPI spec and the shared specs disagree?
- **Decision**: Split by concern. The OpenAPI spec generated by the backend is authoritative for wire shape (paths, fields, types). The shared specs are authoritative for behavior. A generated spec that breaks a shared rule is a backend bug.
- **Alternatives**: Shared specs always win; OpenAPI always wins.
- **Depends on**: —

### D4 — Base path and versioning
- **Question**: What base path and versioning scheme does the API use?
- **Decision**: All endpoints live under `/api/v1`. Additive changes stay in v1; breaking changes require a new major version path (`/api/v2`).
- **Alternatives**: `/api` without versioning; `/api` plus a version header.
- **Depends on**: D3

### D5 — Field naming
- **Question**: How are JSON field names written?
- **Decision**: camelCase.
- **Alternatives**: snake_case.
- **Depends on**: —

### D6 — Timestamps
- **Question**: How are timestamps sent?
- **Decision**: ISO 8601 strings in UTC with exactly millisecond precision and a `Z` suffix, never an offset, e.g. `2026-11-04T09:15:30.123Z`.
- **Alternatives**: ISO 8601 UTC with variable precision; epoch milliseconds.
- **Depends on**: —

### D7 — Null and absent values
- **Question**: How are optional or empty values represented?
- **Decision**: Every documented response field is always present. `null` is a valid value only for fields explicitly documented as nullable, meaning the value does not exist. In v1 no field is nullable, so `null` does not appear. Nullable fields may be added later.
- **Alternatives**: Nullable everywhere optional; omit empty fields.
- **Why**: The user did not want a blanket ban on null, because it is a valid way to express that a future value does not exist.
- **Depends on**: —

### D8 — Unknown fields
- **Question**: What happens with fields the receiver does not know?
- **Decision**: The backend ignores unknown request fields. Clients ignore unknown response fields.
- **Alternatives**: Reject unknown request fields with a validation error.
- **Why**: Additive changes never break older clients or backends.
- **Depends on**: D4

### D9 — Error shape
- **Question**: What shape does every error response have?
- **Decision**: RFC 9457 problem details (`application/problem+json`) with `type`, `title`, `status`, `detail`, plus a stable machine-readable `code` and a `fieldErrors` array of `{ field, code }` entries.
- **Alternatives**: Custom `{ code, message, fieldErrors }` envelope.
- **Depends on**: —

### D10 — Error messages
- **Question**: Who are `title` and `detail` for?
- **Decision**: English text for developers only. Clients never show backend text; they map `code` and field codes to their own localized strings.
- **Alternatives**: Backend text shown to users.
- **Depends on**: D9

### D11 — UUID format
- **Question**: How are UUIDs written, and what happens with a malformed UUID in a path?
- **Decision**: The backend always sends UUIDs in lowercase canonical 8-4-4-4-12 hex form and accepts any letter case. A malformed UUID in a path behaves exactly like a non-existent one (404 NOT_FOUND).
- **Alternatives**: Malformed path UUID returns 400.
- **Why**: Consistent with treating other users' data as not found.
- **Depends on**: —

### D12 — Error code catalog
- **Question**: Which top-level error codes exist in v1?
- **Decision**: A closed list: 400 `VALIDATION_FAILED` (field rules broken, with fieldErrors), 400 `MALFORMED_REQUEST` (unparseable JSON, wrong types), 401 `UNAUTHENTICATED` (access token missing, invalid or expired), 401 `INVALID_CREDENTIALS` (wrong login email or password), 401 `INVALID_REFRESH_TOKEN` (refresh token unknown, expired or revoked), 404 `NOT_FOUND` (missing or another user's resource), 404 `ROUTE_NOT_FOUND` (unknown endpoint), 409 `CONFLICT` (uniqueness clash, with fieldErrors), 413 `PAYLOAD_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA_TYPE`, 422 `INVALID_EXPORT_FILE`, 429 `RATE_LIMITED` (with `Retry-After`), 500 `INTERNAL_ERROR`. 403 is never used for ownership. Adding a code is additive; clients handle unknown codes by HTTP status.
- **Alternatives**: One code per HTTP status only.
- **Depends on**: D9

### D13 — Uniqueness clashes
- **Question**: How is a uniqueness clash (email, board key, label name) reported?
- **Decision**: 409 `CONFLICT` with a field error `{ field, code: ALREADY_USED }`.
- **Alternatives**: 400 `VALIDATION_FAILED` with `ALREADY_USED`; specific top-level codes per clash.
- **Depends on**: D12

### D14 — Field error codes
- **Question**: Which field error codes exist?
- **Decision**: A closed list: `REQUIRED`, `TOO_SHORT`, `TOO_LONG`, `INVALID_CHARACTER`, `INVALID_FORMAT`, `INVALID_VALUE`, `PASSWORD_TOO_WEAK`, `ALREADY_USED`, `OUT_OF_RANGE`. `field` is the JSON property path in the request, e.g. `name`, `labelIds[2]`.
- **Alternatives**: Generic `REQUIRED` / `INVALID` / `ALREADY_USED` only.
- **Depends on**: D9

### D15 — Limits in field errors
- **Question**: Do field errors include the broken limit?
- **Decision**: Yes. Field errors for length or range limits carry `min` and/or `max`.
- **Alternatives**: Codes only.
- **Depends on**: D14

### D16 — IDs referenced in request bodies
- **Question**: What happens when a body references a non-existent or foreign ID (label to attach, target column of a move)?
- **Decision**: 404 `NOT_FOUND`, the same as a path ID.
- **Alternatives**: 400 with a field error.
- **Depends on**: D12

### D17 — Error precedence
- **Question**: Which error wins when several rules are broken?
- **Decision**: In order: authentication (401); request parsing, size and media type (400 `MALFORMED_REQUEST`, 413, 415); not found for path and body references (404); validation (400 `VALIDATION_FAILED` with all field errors); uniqueness (409).
- **Alternatives**: Validation before not found.
- **Depends on**: D12, D16

### D18 — Update semantics
- **Question**: How do updates work?
- **Decision**: PATCH with partial bodies. Only sent fields change.
- **Alternatives**: PUT full replace.
- **Why**: Fits last write wins: a rename does not overwrite a concurrent description edit.
- **Depends on**: —

### D19 — Success responses
- **Question**: What do successful responses return?
- **Decision**: Create returns 201 with the full resource. Update and move return 200 with the full updated resource. Delete returns 204 with no body.
- **Alternatives**: Always 200 with resource; minimal bodies.
- **Depends on**: D18

### D20 — Move target
- **Question**: How is a move target given?
- **Decision**: `position` is the item's index after the move: 0..n-1 within the same container, 0..n when moving a card into another column with n cards. Anything else is rejected with 400 `VALIDATION_FAILED`, field `position`, code `OUT_OF_RANGE`.
- **Alternatives**: Clamp to the valid range; relative before/after sibling.
- **Depends on**: D14

### D21 — Move result
- **Question**: What does a move response contain?
- **Decision**: All items of the affected containers with their positions: all columns of the board for a column move; the cards of the source and target column for a card move.
- **Alternatives**: Only the moved item.
- **Depends on**: D19, D20

### D22 — Pagination
- **Question**: Are list endpoints paginated in v1?
- **Decision**: No. Lists return all items. Adding pagination later is a breaking change for v2.
- **Alternatives**: Cursor pagination from the start.
- **Depends on**: D4

### D23 — List order
- **Question**: What order do the board list and label list have?
- **Decision**: Boards by updated time descending, ties broken by created time descending and then by ID. Labels by case-folded name.
- **Alternatives**: Boards by created time ascending; boards by name.
- **Depends on**: D22

### D24 — Access token use
- **Question**: How do clients send and track the access token?
- **Decision**: `Authorization: Bearer <token>`. Clients treat the token as opaque and never decode it; auth responses include `accessTokenExpiresAt`. On 401 `UNAUTHENTICATED` a client refreshes once, shared across concurrent requests, and retries; a failed refresh ends the session on that client.
- **Alternatives**: Clients may read JWT claims.
- **Depends on**: D6, D12

### D25 — Refresh token transport
- **Question**: How do web and mobile receive and send the refresh token?
- **Decision**: Web: refresh token in an httpOnly, Secure, SameSite=Strict cookie scoped to the auth path; access token kept in memory. Mobile: access and refresh tokens in the JSON body, stored by the app in secure platform storage. Login, register and refresh requests carry `refreshTokenTransport: "COOKIE" | "BODY"`; with `COOKIE` the refresh token never appears in a response body.
- **Alternatives**: JSON body everywhere; separate web endpoints; cookie and body together.
- **Depends on**: —

### D26 — Token lifetimes and rotation
- **Question**: How long do tokens live and how does refresh work?
- **Decision**: Access token 15 minutes. Refresh token 30 days. Every refresh issues a new refresh token valid for 30 days and invalidates the old one (sliding expiry). A session ends after 30 days without a refresh.
- **Alternatives**: Absolute 30 days from login; no rotation.
- **Depends on**: D25

### D27 — Refresh token reuse
- **Question**: What happens when an already-rotated refresh token is used?
- **Decision**: It counts as theft: the whole session is revoked, including its current refresh token, and the request fails with 401 `INVALID_REFRESH_TOKEN`.
- **Alternatives**: Reject only that token; short grace period.
- **Depends on**: D26

### D28 — Logout scope
- **Question**: What does logout revoke?
- **Decision**: Only the current session. Other devices stay logged in.
- **Alternatives**: All sessions; chosen per call.
- **Depends on**: D26

### D29 — Rate limiting
- **Question**: Which endpoints are rate limited?
- **Decision**: Login, register and refresh only. Over the limit: 429 `RATE_LIMITED` with `Retry-After` in seconds. Exact limits are a backend setting, not part of the shared contract.
- **Alternatives**: All endpoints; none in v1.
- **Depends on**: D12

### D30 — Edge cases for delete and patch
- **Question**: What happens with DELETE of a missing item, and PATCH with `null` or `{}`?
- **Decision**: DELETE of a missing item returns 404 `NOT_FOUND`. `null` for a non-nullable field fails with `VALIDATION_FAILED`, code `REQUIRED`. An empty PATCH returns 200 and changes nothing, including timestamps.
- **Alternatives**: Idempotent DELETE returning 204.
- **Depends on**: D7, D18

### D31 — Request body size
- **Question**: What size limit applies to normal JSON requests?
- **Decision**: 256 KB. Larger bodies fail with 413 `PAYLOAD_TOO_LARGE`. The import file keeps its own 5 MB limit.
- **Alternatives**: 1 MB; no shared limit.
- **Depends on**: D12

### D32 — CORS
- **Question**: Does the API accept cross-origin browser requests?
- **Decision**: No. Same-origin only in v1. Web development reaches the local backend through a dev-server proxy.
- **Alternatives**: Allow a configured origin list.
- **Depends on**: D25

### D33 — Export file shape
- **Question**: What does the export file look like?
- **Decision**: A JSON object with `format: "cardigan.board"`, `formatVersion: 1`, `exportedAt`, and `board` holding `name`, `key`, `labels` (name and color of each label used on the board) and `columns` in order, each with `name` and `cards` in order. Each card has `number`, `title`, `description`, `labels` (label names), `createdAt`, `updatedAt`. No UUIDs and no positions; order is array order. Unknown fields are ignored on import.
- **Alternatives**: Include UUIDs and positions.
- **Depends on**: D5, D6

### D34 — Card numbers on import
- **Question**: Do imported cards keep their numbers?
- **Decision**: Yes; display IDs survive a round trip. Numbers must be unique positive integers within the file. New cards in the imported board get numbers above the highest number in the file.
- **Alternatives**: Renumber from 1.
- **Depends on**: D33

### D35 — Highest assigned number in the file
- **Question**: Should the export carry the board's highest number ever assigned?
- **Decision**: No. The imported board continues above the highest card number in the file.
- **Alternatives**: A `lastCardNumber` field.
- **Depends on**: D34

### D36 — Timestamps on import
- **Question**: What happens to created and updated times on import?
- **Decision**: All created and updated times of imported data are set to the import time. Timestamps in the file are informational only.
- **Alternatives**: Keep times from the file.
- **Depends on**: D33

### D37 — Label mapping on import
- **Question**: How are labels in the file mapped?
- **Decision**: A file label whose case-folded name matches an existing label of the user reuses that label and keeps its existing color. Other file labels are created with the color from the file.
- **Alternatives**: Always create; reuse only on name and color match.
- **Depends on**: D33

### D38 — Board key clash on import
- **Question**: What happens when the imported key is already used?
- **Decision**: The import fails with 409 `CONFLICT`, field `key`, code `ALREADY_USED`, and nothing is stored. The client may retry the same file with an optional key override that replaces the file's key.
- **Alternatives**: Backend picks a free key.
- **Depends on**: D13

### D39 — Import upload
- **Question**: How is the file uploaded and how big may it be?
- **Decision**: `multipart/form-data` with a `file` part and an optional `key` part. Maximum file size 5 MB; larger fails with 413 `PAYLOAD_TOO_LARGE`.
- **Alternatives**: Raw JSON body with key as a query parameter.
- **Depends on**: D38

### D40 — Import validation errors
- **Question**: How are problems inside an import file reported?
- **Decision**: 422 `INVALID_EXPORT_FILE` with an empty `fieldErrors`, for every problem inside the file: unparseable JSON, a wrong `format`, an unknown `formatVersion` and rule violations. The response does not say what failed. The backend stops at the first violation and logs its JSON path and rule. An invalid `key` part is not file content and returns 400 `VALIDATION_FAILED` with a field error for `key`. Import is all or nothing.
- **Alternatives**: `fieldErrors` with JSON paths into the file.
- **Why**: The designs have one "Not a Cardigan export" state and no client shows details. Stopping at the first violation also keeps the error response small for crafted files.
- **Depends on**: D12, D14

### D41 — Columns on import
- **Question**: Does an imported board get default columns?
- **Decision**: No. It has exactly the file's columns, even zero.
- **Alternatives**: Default columns when the file has none.
- **Depends on**: D33

### D42 — Export file name
- **Question**: What file name does the export suggest?
- **Decision**: `<KEY>-<yyyy-MM-dd>.json` via Content-Disposition, date in UTC, e.g. `CRD-2026-11-04.json`.
- **Alternatives**: Board name slug; client decides.
- **Depends on**: —

### D43 — Platforms and compatibility
- **Question**: Which platforms are targeted, and is the change breaking?
- **Decision**: Backend, Android, iOS and web. Not breaking.
- **Alternatives**: Android and iOS as one platform.
- **Why**: No API exists yet, so nothing has to migrate.
- **Depends on**: —

## Facts

- Other users' data must behave exactly like a non-existent identifier — source: `openspec/specs/domain-user/spec.md`
- Changes to a deleted card fail with not found — source: `openspec/specs/domain-ordering/spec.md`
- Order is defined only by dense positions 0..n-1; last write wins with no version check — source: `openspec/specs/domain-ordering/spec.md`
- All entities have backend-assigned UUIDs and backend-set UTC created/updated times — source: `openspec/specs/domain-*/spec.md`
- Card labels are presented sorted by case-folded name — source: `openspec/specs/domain-card/spec.md`
- Board key 2–5 letters A–Z, unique among a user's existing boards; card numbers per board, never reused — source: `openspec/specs/domain-board/spec.md`, `openspec/specs/domain-card/spec.md`
- Text normalization, character and length rules — source: `openspec/specs/text-length/spec.md`
- Import max file size 5 MB, key clash dialog asks for a different key, all boards load at once — source: `docs/design/DECISIONS.md`
- Backend generates the OpenAPI spec code-first with SpringDoc; clients generate code from it; JWT 15 min / 30 days — source: `docs/breakdown/OVERVIEW.md`
- Production serves web and API behind one reverse proxy on the same domain — source: `docs/breakdown/chunks/41-infra-vps.md`

## Out of scope

- Individual endpoints, paths and DTOs (generated code-first by the backend feature chunks)
- Full auth flows (register, login, refresh, logout request/response details beyond the token conventions)
- Feature behavior for boards, columns, cards and labels
- Platform implementation details (token storage libraries, HTTP clients, generators)

## Deferred

- Board read shape (full board in one call or not) — settle before: implementation (`be-boards`)
- How the exported OpenAPI spec is handed to clients and regenerated — settle before: implementation (`be-common`)
- Card labels set via full replace vs. attach/detach — settle before: implementation (`be-cards`)
- JWT signing algorithm — settle before: implementation (`be-common`)
- Exact rate limit values — settle before: implementation (`be-auth`)
- Client request timeouts on slow networks — settle before: implementation (connect chunks)
