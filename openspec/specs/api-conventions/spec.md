# api-conventions Specification

## Purpose

Defines the conventions every Cardigan API endpoint follows on the wire, so the backend and all clients agree on paths, versioning, data formats and request semantics before any endpoint exists.

## Requirements

### Requirement: Generated OpenAPI is authoritative for wire shape
The OpenAPI document generated by the backend SHALL be the authoritative source for paths, methods, field names and field types. The shared specs SHALL be the authoritative source for behavior. When the generated document contradicts a shared spec, the backend SHALL be changed to match the shared spec.

#### Scenario: Responses match the document
- **WHEN** any documented endpoint responds
- **THEN** the response body validates against that endpoint's schema in the generated OpenAPI document

#### Scenario: Behavior contradiction
- **WHEN** a client creates a board with a name of normalized length 101, even if the generated document allows longer names
- **THEN** the response is 400 `VALIDATION_FAILED` with code `TOO_LONG` and `max` 100

### Requirement: All endpoints use a versioned base path
Every API endpoint SHALL be served under the base path `/api/v1`. Within a major version, the API SHALL only change in ways that keep existing clients working. A breaking change SHALL be served under a new major version path such as `/api/v2`.

#### Scenario: Endpoint paths
- **WHEN** the generated OpenAPI document is inspected
- **THEN** every path starts with `/api/v1/`

#### Scenario: Unknown path
- **WHEN** an authenticated client calls a path under `/api/v1/` that no endpoint serves
- **THEN** the response is 404 with the error code `ROUTE_NOT_FOUND`

#### Scenario: Unknown path without a token
- **WHEN** a client without a token calls such a path
- **THEN** the response is 401 `UNAUTHENTICATED`

#### Scenario: Wrong method
- **WHEN** an authenticated client calls an existing path with a method it does not serve
- **THEN** the response is 404 `ROUTE_NOT_FOUND`

### Requirement: Changes within a version are additive
Within a major version, the API SHALL only add endpoints, add response fields, add optional request fields, or add error codes. It SHALL NOT remove or rename fields, change field types, make an optional request field required, or change the meaning of existing values.

#### Scenario: Release compared with the last v1 document
- **WHEN** the generated OpenAPI document of a new build is compared with the last released v1 document
- **THEN** no path, method, response field or enum value was removed or renamed, no field type changed, and no optional request field became required

### Requirement: JSON with camelCase field names
Request and response bodies SHALL be JSON encoded as UTF-8, except where a spec defines another format. Field names SHALL be camelCase, such as `createdAt` or `boardId`.

#### Scenario: Field names
- **WHEN** the generated OpenAPI document is inspected
- **THEN** every field name matches `^[a-z][a-zA-Z0-9]*$`

### Requirement: Timestamps are UTC strings with milliseconds
Every timestamp on the wire SHALL be an ISO 8601 string in UTC with exactly three fractional digits and the suffix `Z`, in the form `YYYY-MM-DDTHH:mm:ss.sssZ`. Offsets other than `Z` SHALL NOT be sent.

#### Scenario: Timestamp format
- **WHEN** a card was created on 4 November 2026 at 09:15:30.123 UTC
- **THEN** its `createdAt` is `2026-11-04T09:15:30.123Z`

#### Scenario: Whole second
- **WHEN** a timestamp falls exactly on a second
- **THEN** it is still sent with three fractional digits, such as `2026-11-04T09:15:30.000Z`

### Requirement: UUIDs are lowercase canonical strings
The backend SHALL send every UUID as a lowercase string in the canonical 8-4-4-4-12 hexadecimal form. It SHALL accept UUIDs in any letter case. Clients SHALL treat UUIDs as opaque values.

#### Scenario: UUID in a response
- **WHEN** the backend returns a board identifier
- **THEN** it has the form `3f2b8c1e-9a4d-4e2f-8b1a-0c9d7e6f5a43`, all lowercase

#### Scenario: Uppercase UUID in a request
- **WHEN** a client sends a board identifier in uppercase
- **THEN** the backend treats it as the same identifier

### Requirement: Malformed path identifiers are not found
A path segment that should be a UUID but is not a valid UUID SHALL produce the same 404 `NOT_FOUND` response as a valid UUID that does not exist.

#### Scenario: Malformed board ID
- **WHEN** a client requests a board with the path identifier `abc`
- **THEN** the response is 404 with the error code `NOT_FOUND`

### Requirement: Documented fields are always present
Every field documented for a response SHALL always be present in that response. The only exceptions are `min` and `max` in field errors, present only as `api-errors` defines, and `refreshToken` in auth responses, present only as `api-auth-tokens` defines.

#### Scenario: Empty description
- **WHEN** a card has no description
- **THEN** the response contains `"description": ""`, not `null` and not a missing field

#### Scenario: No labels
- **WHEN** a card has no labels
- **THEN** the response contains an empty labels array

### Requirement: Null values
`null` SHALL only be sent for a field documented as nullable, and then it SHALL mean that the value does not exist. Fields that are not documented as nullable SHALL never be `null`. In v1 no response field is documented as nullable. A nullable field MAY be added later as a new field.

#### Scenario: No nullable fields in v1
- **WHEN** the generated OpenAPI document is inspected
- **THEN** no response field is marked nullable

### Requirement: Unknown fields are ignored
The backend SHALL ignore request fields it does not know. Clients SHALL ignore response fields they do not know.

#### Scenario: Newer client field
- **WHEN** a request contains a field the backend does not know
- **THEN** the backend processes the request as if the field were absent

#### Scenario: Newer backend field
- **WHEN** a response contains a field the client does not know
- **THEN** the client processes the response as if the field were absent

### Requirement: Updates are partial
Updates to an existing resource SHALL use PATCH. Only the fields present in the request SHALL change. Absent fields SHALL keep their current values.

#### Scenario: Rename keeps the description
- **WHEN** device A changes a card's description and device B then sends a PATCH with only a new title
- **THEN** the card has device B's title and device A's description

### Requirement: Null and empty updates
A PATCH that sets a field not documented as nullable to `null` SHALL be rejected with a validation error for that field with the field error code `REQUIRED`. A PATCH with an empty object SHALL succeed and change nothing, including timestamps.

#### Scenario: Null title
- **WHEN** a client sends a PATCH with `"title": null` for a card
- **THEN** the response is 400 `VALIDATION_FAILED` with a field error for `title` with code `REQUIRED`

#### Scenario: Empty patch
- **WHEN** a client sends a PATCH with `{}` for a card
- **THEN** the response is 200 with the unchanged card, and its updated time and its board's updated time do not change

### Requirement: Success status codes and bodies
Creating a resource SHALL return 201 with the full created resource. Updating or moving a resource SHALL return 200 with the full updated resource or the result a spec defines for it. Deleting a resource SHALL return 204 with no body.

#### Scenario: Create a label
- **WHEN** a client creates a label
- **THEN** the response is 201 and the body is the full label with its identifier, normalized name, color and timestamps

#### Scenario: Delete a card
- **WHEN** a client deletes a card
- **THEN** the response is 204 with an empty body

### Requirement: Deleting a missing resource is not found
Deleting a resource that does not exist, was already deleted, or belongs to another user SHALL return 404 `NOT_FOUND`.

#### Scenario: Delete twice
- **WHEN** a client deletes a card and then sends the same delete again
- **THEN** the second response is 404 with the error code `NOT_FOUND`

### Requirement: Move target is the final position
A move request SHALL give the target as `position`, the item's index after the move. Within the same container the valid range SHALL be 0 to n-1 for n items. Moving a card into another column with n cards SHALL allow 0 to n. Any other integer, of any size, SHALL be rejected with a validation error for `position` with the code `OUT_OF_RANGE`.

#### Scenario: Move to the end of another column
- **WHEN** a card is moved into a column with 3 cards with position 3
- **THEN** the card is last in that column at position 3

#### Scenario: Position too large
- **WHEN** a board has 3 columns and a column is moved to position 3
- **THEN** the response is 400 `VALIDATION_FAILED` with a field error for `position` with code `OUT_OF_RANGE`, and no position changes

#### Scenario: Negative position
- **WHEN** a card is moved to position -1
- **THEN** the response is 400 `VALIDATION_FAILED` with a field error for `position` with code `OUT_OF_RANGE`

#### Scenario: Huge position
- **WHEN** a card is moved to position 1099511627776
- **THEN** the response is 400 `VALIDATION_FAILED` with a field error for `position` with code `OUT_OF_RANGE`

#### Scenario: Same-column position equal to n
- **WHEN** a card in a column of 3 cards is moved within that column to position 3
- **THEN** the response is 400 `VALIDATION_FAILED` with a field error for `position` with code `OUT_OF_RANGE` and `max` 2

### Requirement: Clients recover from a stale move
Because clients can hold stale data, `OUT_OF_RANGE` on a move is an expected outcome. A client that receives it SHALL reload the affected board and tell the user the move did not apply. A stale position that is still in range SHALL be applied as sent.

#### Scenario: Move on a stale column
- **WHEN** a client shows 5 cards in a column that now has 3, and a move within it to position 4 returns `OUT_OF_RANGE`
- **THEN** the client reloads the board and tells the user the move did not apply

### Requirement: Move responses contain all affected items
A successful column move SHALL return all columns of the board with their positions. A successful card move SHALL return all cards of the source column and of the target column with their positions. Within the same column, that column's cards SHALL be returned once.

#### Scenario: Column move result
- **WHEN** a board has columns A, B, C and C is moved to position 0
- **THEN** the response contains C, A, B with positions 0, 1, 2

#### Scenario: Card move across columns
- **WHEN** a card is moved from column X to column Y
- **THEN** the response contains every card of X and every card of Y with their new positions

#### Scenario: Move within a column
- **WHEN** a card is moved within a column of 3 cards to position 2
- **THEN** the response contains each of the 3 cards exactly once with positions 0, 1, 2

### Requirement: Lists are complete and unpaginated
List endpoints SHALL return all matching items in one response, without pagination. Ordered items within a list SHALL carry their position where the domain defines one.

#### Scenario: Many boards
- **WHEN** a user with 300 boards loads the board list
- **THEN** all 300 boards are returned in one response

### Requirement: Board list order
The board list SHALL be sorted by updated time, newest first. Boards with the same updated time SHALL be sorted by created time, newest first, and then by identifier as a lowercase string in ascending order. Times SHALL be compared at the millisecond precision sent on the wire.

#### Scenario: Recently edited board first
- **WHEN** a user edits a card on their oldest board
- **THEN** that board is first in the next board list response

#### Scenario: Full tie
- **WHEN** two boards have the same updated and created times
- **THEN** the board with the lower identifier string comes first

### Requirement: Label list order
The label list SHALL be sorted by the Unicode code points of the case-folded name, as defined in `domain-label`, compared in ascending order, independent of locale. Card labels and export file labels SHALL use the same order.

#### Scenario: Mixed case names
- **WHEN** a user has labels `frontend`, `Bug` and `api`
- **THEN** the label list returns `api`, `Bug`, `frontend`

#### Scenario: Non-ASCII names
- **WHEN** a user has labels `Zebra`, `Äpfel` and `apple`
- **THEN** the label list returns `apple`, `Zebra`, `Äpfel`

### Requirement: Request body size limit
A request body larger than 262,144 bytes (256 KB) SHALL be rejected with 413 `PAYLOAD_TOO_LARGE`, except where a spec defines a different limit for an endpoint. The limit SHALL apply to the bytes actually received, whether or not the request has a `Content-Length` header, and the backend SHALL stop reading once the limit is passed. Nothing from a rejected request SHALL be stored.

#### Scenario: Oversized body
- **WHEN** a client sends a 300 KB JSON body to create a card
- **THEN** the response is 413 with the error code `PAYLOAD_TOO_LARGE` and nothing is stored

#### Scenario: Exactly at the limit
- **WHEN** a client sends a JSON body of exactly 262,144 bytes
- **THEN** the request is not rejected for its size

#### Scenario: One byte over
- **WHEN** a client sends a JSON body of 262,145 bytes
- **THEN** the response is 413 `PAYLOAD_TOO_LARGE`

#### Scenario: Oversized chunked body
- **WHEN** a client sends a 300 KB JSON body with chunked encoding and no `Content-Length`
- **THEN** the response is 413 `PAYLOAD_TOO_LARGE`

### Requirement: Same-origin only
The API SHALL NOT send `Access-Control-Allow-*` headers on any response. The web app SHALL reach the API from the same origin.

#### Scenario: Request from another origin
- **WHEN** a browser page on another origin calls the API
- **THEN** the backend sends no CORS headers that would allow the browser to read the response

#### Scenario: Preflight
- **WHEN** a browser sends an `OPTIONS` preflight from another origin
- **THEN** the response has no `Access-Control-Allow-*` headers

### Requirement: HTTPS only
Outside local development, the API SHALL be served only over HTTPS. A plain HTTP request SHALL NOT be processed by an endpoint. Release builds of clients SHALL use only an HTTPS base URL.

#### Scenario: Plain HTTP request
- **WHEN** a client sends a request to the production API over plain HTTP
- **THEN** no endpoint processes it

### Requirement: Retries after a lost response
The API has no idempotency keys. Clients SHALL NOT automatically repeat a POST after a network failure with an unknown outcome; they SHALL report the failure and reload the affected data before the user tries again. A client that repeats a DELETE and receives 404 `NOT_FOUND` SHALL treat the item as deleted. Repeating a request after 401 `UNAUTHENTICATED` is allowed, because that request was not applied.

#### Scenario: Import response lost
- **WHEN** the connection drops while a client waits for the response to an import
- **THEN** the client does not repeat the upload, reports the failure and reloads the board list

#### Scenario: Repeated delete
- **WHEN** a client repeats a DELETE and receives 404 `NOT_FOUND`
- **THEN** it treats the item as deleted

### Requirement: Backend time can be set in tests
Test setups SHALL be able to set the current time the backend uses for token lifetimes, timestamps and export names. Production deployments SHALL NOT expose this.

#### Scenario: Time moved forward
- **WHEN** a test setup moves the backend time forward by 16 minutes after a login
- **THEN** the access token from that login fails with 401 `UNAUTHENTICATED`
